# Documenso AMD64 build verification

`.github/workflows/documenso-build.yml` builds the existing reviewed provider source on a standard Ubuntu 24.04 AMD64 runner. It runs manually or when a PR to develop touches that workflow or either of its two pinned patches. It does not publish an image, deploy a service, start Documenso, connect a database or use production configuration.

Inputs are fixed: upstream `8707e33c124e4b1a68dde92d5e05178c9aabd0be`, security patch `07b5538df181f9a8d12f3048fb95263a80d9c5c5252dfd515a3c26bec82058ae`, compatibility patch `3c1154411b0e0196e962932253f018700ad71fc3642e0bd4535f302def1cdd6f` and AMD64 Node base `13cf9d4c07e847a41b81b0f24461bea41ec8bcd0a5c00e2ab88e2ba1159b54d4`. The compatibility patch already contains the older countdown correction. The workflow checks patch applicability, dependency security floors, the pinned base and prepared Dockerfile hash `bfe41109f9a1fab790d8d2fd1daadfb6226d175328f7c40741e19936743e200c` before building.

The [first security refresh build](https://github.com/saeloun/miru-web/actions/runs/42882587721) passed source/resource preparation but failed at the base-stage `apk upgrade --no-cache 'zlib>=1.4-r0'` command: `upgrade` accepts package names. The corrected command is `apk add --no-cache 'zlib>=1.4-r0'`; [`add` accepts constraints](https://github.com/alpinelinux/apk-tools/blob/master/doc/apk-add.8.scd) and resolves installed packages against that floor. Source/recipe checks do not exercise Linux APK installation, and the failed run produced no approved replacement artifact.

The patched Dockerfile retains the existing Zod, MailChannels and dependency guards and adds regression checks for redirect credentials across JavaScript realms, hostile comma query serialization, static-path authentication, glob cancellation, bounded minimatch preprocessing, SVG escaping/PNG rendering, installed dependency versions and mandatory SMTP STARTTLS. The SMTP check uses a loopback fixture and `verify()`; it sends no email. The Remix build invokes TypeScript checking before bundling. Network-none checks verify Linux/x64, default UID 1001, all four installed Zod entrypoints, every installed copy of the refreshed dependency families and Alpine `zlib>=1.4-r0`; they do not start the application or run migrations/signing. Resource admission refuses less than 12 GiB disk/RAM; the builder is limited to 12 GiB, four CPUs and two parallel operations. A resource failure is not a passing build; no cleanup or paid-runner fallback occurs.

The refresh pins `follow-redirects 1.16.2`, `systeminformation 5.33.16`, `qs 6.16.1`, `@hono/node-server 2.1.3` and `satori 0.33.5`. Version-scoped overrides move glob 10/11/13 to 14.0.2 and minimatch 9/10 to 11.0.1; glob's new minimatch 11 dependency resolves to 11.0.4. Legacy glob 7 and minimatch 3/5 retain their APIs and are outside these specific advisory ranges. Parent-package API checks cover the scoped overrides. After production pruning, the final image guard scans nested packages in the root and real `apps/*` and `packages/*` workspace directories; it skips symlink directories to avoid loops and reads outside `/app`. This compatibility evidence does not replace the AMD64 build or fresh image scan.

The initial image scan reported 13 findings: two HIGH, ten MEDIUM and one LOW. The refreshed recipe targets all 13; it does **not** change those already-built image bytes or establish a clean replacement image. Rebuild and scan the actual new archive without suppressions before acceptance. The [follow-redirects advisory](https://github.com/follow-redirects/follow-redirects/security/advisories/GHSA-mrwp-f3q8-3g9p) rates the credential issue Moderate, while the scanner rated it HIGH. The [systeminformation HIGH](https://github.com/sebhildebrandt/systeminformation/security/advisories/GHSA-3f7j-7jwc-fxfj) concerns Windows PowerShell service-name injection; its presence in this Linux image does not establish Linux code execution.

For SMTP providers requiring STARTTLS, set `NEXT_PRIVATE_SMTP_REQUIRE_TLS=true` with the provider's supported port and `NEXT_PRIVATE_SMTP_SECURE=false`. This private operator flag applies to both environment and configured SMTP transports, refuses missing STARTTLS before authentication, and takes precedence over unsafe `ignoreTLS`. It defaults to false so local plaintext QA remains available. Hostnames and credentials are not supplied by the patch; provider connectivity and delivery require separate checks.

After successful checks, the workflow retains `documenso-amd64-<checkout SHA>-<run ID>-<attempt>` for **one day**. It contains the Docker archive `image.tar.gz`, `SHA256SUMS`, `provenance.json`, upstream AGPLv3 `LICENSE`, both verified patches and the prepared Dockerfile under `source/`, plus the upstream/source pointers. Provenance records the prepared Dockerfile and license hashes. `docker_image_id` and `archive_config_sha256` are recorded separately because Docker image-store object IDs are not always the config hash. No environment/config dump is exported.

Artifact metadata and checksums are self-attested integrity information, not authentication or approval. Before downloading, independently verify the trusted GitHub repository, run, event, attempt, and reviewed workflow/source expectations for the approved revisions. After downloading, verify the recorded digest and included source bytes. A modified workflow can declare its own hashes; these files cannot authorize automatic deployment.

For a pull request, `checkout_revision` and the image build label identify GitHub's tested merge commit; `pull_request_head_revision` identifies the PR head. These can differ. Compare each with its corresponding run context rather than treating the run's head SHA as the tested merge SHA. Included source files keep the patches and prepared Dockerfile available independently of a temporary merge-commit URL.

The archive checksum and config hash bind the produced bytes; they do not prove host import, provider startup, email, TLS, certificate suitability, signing, callbacks, backup/restore or production acceptance. Host transport/test deployment requires separate review. A failed job supplies no usable approved artifact. Rerun only after inspecting its actual failure; do not substitute the old ARM64 QA image.

The manual action becomes available when this workflow exists on the default branch; its path-limited PR trigger can verify the workflow before that landing. There are no arbitrary source, image or publish inputs. Existing Miru application build/release workflows are unchanged.
