# Consultant billing identity and accounts review

Sonam #2458 sections 1/10 require engagement-scoped legal/billing/tax facts before payment readiness and immutable parties for eventual consultant invoices. The user delegated implementation decisions and asked to continue shipping, with parallel resources. This delivery implements the full identity/evidence/review and new-payment binding workflow. Buyer legal-entity snapshots, invoice issuance/numbering/PDF and statutory tax calculation remain required later dependencies; this record is not a tax certificate or invoice consent.

## Approach

Use two append-only records: self-submission versions and accounts-review events bound to the exact submission. Reusing mutable User/EmployeeRecord fields would change historic invoice parties and broaden private bank/profile access. Overloading employee TaxDeclaration would confuse supplier identity with employee deduction claims. Reuse their private upload conventions and the invoice-authorization chain/retry patterns, with no new dependency or general workflow engine.

## Facts and access

- Dedicated `/settings/billing-identity`, default self with optional validated target user, and a narrow accounts-preparation link. Display current workspace/consultant and version status. A kept configured consultant may submit their own facts, including prehire/after exit for past services, while payroll is enabled; existing history stays readable when disabled. No impersonation, automatic consent or payment action. Deleted users/employments and workspace mismatches remain denied.
- Active owners/admins and explicitly assigned accounts reviewers may inspect/review this resource. A bookkeeper needs an actual same-company run assignment; no generic coworker profile/bank access. No self-review, even for an owner. Recheck active company-local membership/role/current selected workspace at every action and after reading private file bytes.
- Structured fields: `legal_name`, `address_line_1`, optional `address_line_2`, `city`, `state`, six-digit string `postal_code`, `country` fixed `IN`; `pan_status` (`provided`, `not_available`), `pan_number`, `pan_reason`; `gst_status` (`registered`, `not_registered`, `needs_review`), `gst_number`, `gst_scheme` (`regular`, `composition`, `other`), `gst_reason`. No default exemption/registration. Missing PAN and unresolved GST can be explicitly submitted, not disguised as zero tax. Unregistered/other/unresolved facts require a reason; provided PAN/registered GST require their values and private evidence.
- Validate scalar types/allowed keys and bounded text before storage. PAN is five uppercase letters, four digits and one letter; GST is a 15-character uppercase identifier with two leading digits, the same declared PAN in positions 3–12 and three alphanumeric suffix characters. Basic syntax and PAN consistency only: do not claim checksum, registration status or government verification. Do not hard-code the 14th GST character to Z; primary GSTN material shows other registration types. Normalize only explicit text fields/identifier case, preserving postal strings. No funding-bank inference or automatic tax rates/thresholds.
- Saved facts, review reasons and evidence manifests are encrypted; model inspection/filtering and request-root filters prevent identifiers/addresses/reasons from entering logs/audits. Dedicated authorized self/reviewer resource can return facts for editing/review; ordinary profile/payroll snapshots receive only opaque IDs/digests/status. Default read-only display masks tax IDs. Never put private facts in URL parameters, analytics or browser storage.

## Evidence and immutable history

One PAN file and one GST file, each PDF/JPEG/PNG, sniffed type, maximum 5 MiB, private service. Use neutral server filenames by evidence kind/type; never persist a caller filename containing a tax identifier. No caller-supplied blob IDs or public URLs. A correction can explicitly reuse its predecessor's evidence only within the same employment and unchanged corresponding identifier/status/scheme. Replacing evidence makes a new submission. Preserve old evidence and its source manifest.

The server computes file SHA256/type/size before uploading and binds the immutable submission digest to facts and evidence. Upload new private blobs successfully before committing a submission, so a failed postcommit upload cannot leave an approved-looking missing file. Attach only uploaded server-owned blobs or validated predecessor blobs. Exact-command replay resolves before creating new blobs. Clean up owned unattached blobs on failed/conflicting creation without purging historical/shared evidence. Downloads and approval validate the retained kind/blob/manifest and reauthorize after the read; missing/tampered evidence fails closed without leaking values. Immutable profile/review rows and tenant/actor/predecessor constraints protect SQL history; evidence references cannot silently change a submitted version.

Submissions require displayed predecessor and a bounded idempotency key; canonical command digest includes normalized facts, evidence-byte identity/reuse choices and predecessor. Review events require displayed submission/current review, bounded key, decision (`approved`, `needs_information`, `rejected`), and reason. Accounts can append a new decision to withdraw earlier approval; old events remain immutable. Existing history remains readable to self/current narrow observers while payroll is disabled, and an eligible reviewer can withdraw an existing approval then; new submissions/approvals stay disabled. Approval requires explicit `manual_tax_reviewed=true`; missing PAN additionally requires `missing_pan_acknowledged=true` and a review reason recording the manual treatment. Registered GST requires provided PAN. Unresolved GST (`needs_review`) cannot be approved. Missing PAN is not treated as exempt or zero withholding: monetary withholding remains the separately reviewed payroll amount. This is a human review receipt, not automated statutory validation.

Serialize mutations on employment and reauthorize under lock. One profile root/successor and unique command; one review chain per submission with a unique successor/command. SQL protects kept actor/tenant/role/assignment/history; the application enforces active dates using the company's resolved timezone, rather than assuming Rails timezone labels are valid PostgreSQL zone names. Reject proxy actors, foreign references, stale heads and UPDATE/DELETE. Exact retries return original receipt plus current state, so old replay cannot reinstate an old profile or approval. History is paginated. Browser retains the exact frozen command and real File references across ambiguous503 and Refresh; explicit retry reuses them, while deliberate edits create a new command. Clear private state on actor/target/workspace changes; do not pretend file selections survive reload.

## Payment/source integration

Keep MonthlyFacts v2 and its monetary/PTO/service-fee contracts byte-for-byte unchanged. Put separately versioned `billing_identity` in each newly prepared consultant line: `{version: "miru-consultant-billing-v1", submission_id, review_id, digest}` with string IDs/opaque keyed digest and no private facts. `Payroll::BillingIdentity#binding` returns only the current approved version; `valid_binding?` checks exact equality. Never infer review from a document, old source schema or caller-supplied ID.

Require the binding in new consultant revision creation and approvals, preparation readiness, Mercury preparation **and old prepared instruction submission**, and new/queued India handoff dispatch. A change/revoked review makes only affected new work not ready and requires refreshed revision/both approvals. Use existing run→employment lock order at money boundaries; profile mutations take employment only and do not acquire run locks in reverse order. Dynamic source validation detects changed bindings; do not rewrite historical revisions.

Preserve persisted protected lines and accepted/submitted bank destinations; accepted partial/full/duplicate/returned credit reconciliation must still work without newly collected identity. A mixed run automatically carries authenticated current persisted lines for actual in-flight Mercury legs or sent/sending/uncertain India handoffs, without requiring retroactive profile collection or rebuilding paid financial facts. Candidate data must match that persisted line except capture timestamp and an optional currently valid billing binding, and match actual immutable bank evidence. Mercury evidence comes from each in-flight leg's revision, not the mutable group's latest-preparation pointer. Queued/failed India reports are unsubmitted and do not receive this exception. Selected attempts to change retained financial inputs are rejected, not silently ignored.

Only authenticated retained lines bypass fresh source/claim/PTO/billing reevaluation during later payroll approvals; every new outbound prepare/submit/dispatch still requires current billing review and strict current source, calculation, claim and PTO checks for that line. An accepted sibling or the delivery's own sending state cannot satisfy those outbound checks. Retained claim reservations and PTO recovery history retain their original revision attribution. A reviewed binding can be adopted as metadata while frozen bank amounts, claims, reports and destinations remain unchanged. India guard digests exclude that new metadata, preserving legacy digests without it. Legacy optional preparation can carry only the explicit billing envelope rather than invented cutoff/tax defaults. Shared retained-line comparison normalizes absent/null preparation and billing-only metadata for recovery comparisons without rewriting persisted India digests. Repeating the original existing India-handoff request returns its immutable receipt without enqueuing another delivery; it does not authorize current dispatch. No blanket v2 grandfathering for new/outbound money. Do not insert new mandatory identity checks into PTO accrual, scalar calculators, MonthlyFacts or accepted-credit recovery. Add explicit synthetic reviewed identity only to new-preparation test contexts; retain a distinct untouched legacy accepted-payment fixture/proof.

## Delivery and verification

Known scope boundary: a retained line with stale source facts or changed resolution
authorship can hold an unsent split leg or an absence-confirmed retry. This delivery
does not rebuild accepted provenance automatically. Keep the hold and reconcile bank
status; never bypass validation or mark an unconfirmed credit. An explicit reviewed
source-refresh/recovery command with preserved claim/PTO attribution is a separate
required increment. This is the low-severity R1 liveness limit from the final scoped
Claude review, not a claim of complete split/retry recovery.

Backend owns profile/review models, policy/service/API, migration/schema/dumper, private files and focused domain/request/SQL/concurrency checks. Frontend owns one page/API/nav/preparation links and real native self→accounts review→correction/retry/evidence/privacy/accessibility proof, with desktop/mobile screenshots and required Vite builds. Root owns payment binding/current-source integration and regression checks; an independent reviewer checks final trust boundaries and exact-head gates. No shared test database or concurrent schema/asset writes.

Prove scalar/format/applicability variants, missing-PAN explicit review, GST unknown blocking, private bytes/filename handling, immutable history and foreign/actor/predecessor constraints, competing review/edit/prepare, exact/ambiguous retries, both provider readiness paths and old-prepared/queued dispatch, source-v2 parity, unchanged monetary/PTO results and real legacy accepted-credit recovery. Local mocks do not prove live transfers, official tax eligibility, Form16/ITR or government verification.
