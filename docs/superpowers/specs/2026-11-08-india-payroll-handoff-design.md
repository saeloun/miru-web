# India consultant payroll handoff

Sonam's #2458 section 8 requires the approved India-funded consultant report to reach accounts, followed by manual transfer/credit recording. Section 6 requires reserved claims and once-only settlement. Email delivery is not evidence of payment. This is the next bounded implementation unit under the owner's existing direction to choose the implementation and keep shipping; it does not complete all of #2458 or enable a bank API.

## Coordinator's implementation decisions

Keep immutable payroll runs, revisions and approvals. Add a payroll-owned handoff beside them rather than using customer invoices, Mercury instructions or hiring records. A single active handoff per run/consultant freezes the approved line, compensation version, Indian bank details, reviewer identities and explicitly confirmed accounts mailbox. The owner enters/confirms the single mailbox; no Saeloun address is silently used for another tenant. The assigned accounts reviewer records actual credit. No transfer is initiated by this feature.

The full report is deliberately included in the accounts email, including the account number requested by Sonam. The review UI masks account numbers and exposes only a keyed `bank_version` fingerprint. Confirmation must POST that displayed version as `expected_bank_digest`; a missing or changed version conflicts before any handoff is written. Refreshing changed bank details resets the owner confirmation/mailbox, so a stale checkbox cannot authorize a new beneficiary. Encrypt the report and email recipient at rest; omit both from SQL, audit, job and mail instrumentation. Sender/reply-to reuse existing mail configuration. Show a warning before sending that the selected mailbox will receive confidential bank/payroll data.

Report fields: consultant, period, legal contracting entity, recorded hours, working days as recorded hours / 8, separately identified leave entries (do not invent approved paid leave where source data has no pay classification), monthly fee, reviewed unpaid hours, approved adjustments and withholding, final fee, itemized reserved reimbursements, total INR payable and bank holder/name/number/IFSC. Include revision digest and handoff ID. Preserve the exact approved snapshot; never rebuild an old email from mutable live amounts.

## Storage and actions

- `PayrollIndiaHandoff`: company/run/revision/employment/creator, encrypted report, line digest, terms ID, bank digest, release and fully-credited timestamps. Database uniqueness prevents two active handoffs for the same run/consultant. Frozen fields are immutable.
- `PayrollIndiaDelivery`: append-only attempt identity/number, handoff, state (`queued`, `sending`, `sent`, `failed`, `uncertain`), timestamps and safe error code. Only its delivery outcome fields change. Durable intent exists before enqueue; a recovery job re-enqueues queued records. Duplicate jobs claim once under a lock. Never send while a DB transaction remains open.
- `PayrollIndiaCredit`: immutable amount in paise, actual date, encrypted transaction reference, keyed reference digest and actor. Company-wide unique normalized reference prevents replay; reuse with a different handoff, amount or date conflicts. No email marks claims paid. Only cumulative actual credit reaching entitlement settles that consultant's exact reserved claims in one transaction; partial credit keeps reservations. Record overpayment visibly rather than silently discarding real credit.

API under the existing run: list, create handoff (owner, expected revision digest, consultant, accounts email, bank confirmation), retry a known failed attempt, reconcile uncertain delivery with recorded evidence and stopped-worker attestation, void a definitely unsent handoff, and record credit (assigned accounts). All writes require the existing explicit current workspace binding and fresh role/entitlement checks. Current owners/assigned accounts can inspect the private masked history. No arbitrary employee sees another consultant's record.

Fresh approval/source/terms/bank/actor checks run before queue and immediately before dispatch. An unchanged approved line can survive another consultant's revision, but the current head must be approved before dispatch. India compares the whole canonically ordered line, omitting only the capture timestamp, rather than Mercury's monetary-only digest. A new revision must not alter a handed-off consultant's report or release its claims. Compensation changes must serialize on the affected run rows and must not retrospectively switch funding or terms for a handed-off month. All mutations use run → handoff → delivery → reservation/expense lock order. Mercury preparation must continue to reject India funding, and India preparation rejects any existing Mercury activity or nonwithdrawn spouse split. Bank/reference digests use a keyed HMAC. Normalize credit references and enforce company-wide uniqueness so one transfer cannot count for two consultants.

Only the frozen consultant's exact expected reservations may settle. If claims changed or disappeared, retain the actual credit evidence and report settlement blocked; roll back every attempted claim change together. A repeated identical credit can safely reattempt settlement after accounts resolves the discrepancy. Historical credit uses frozen values even when source or bank data later changes.

Known-unsent failures can be retried through a new attempt after renewed checks, or voided before a revision. Any dispatch exception that could follow SMTP acceptance is `uncertain`, not automatically retried. A stale `sending` attempt becomes uncertain. Reconciliation requires assigned accounts, a bounded evidence reference, and confirmation the previous worker stopped; only confirmed non-delivery permits a new attempt. Confirmed delivery becomes awaiting payment. Delivered, unresolved, partially credited and credited handoffs cannot be voided or revised: financial cancellation/return replacement is held for the separate reversal workflow, not guessed from an email error.

## UI

Add an India accounts panel to payroll review next to the existing Mercury panel. Per India-funded consultant, show readiness, mailbox, frozen masked bank identity, attempts/history, awaiting-payment/uncertain/partial/credited states and actual credited/remaining/overpaid INR. Owners explicitly confirm the report and send/retry/void. Assigned accounts can record amount/date/reference and resolve an uncertain delivery. Keep forms accessible and disable pending actions without relying on disabled buttons for server authorization. Errors remain safe, actionable codes/messages.

## Verification and boundaries

Focused model/service/request tests cover approval/role/tenant/current-workspace checks; stale terms/bank/source/approval; duplicate clicks/jobs/reference replays; SMTP rejection versus ambiguity; pre-send role revocation; safe retries and void; partial/full/overcredit; reserved-claim races and exactly-once settlement; revisions/funding changes; encrypted storage and logs. Use the real queue and local SMTP for delivery proof, with synthetic data only. Browser tests cover owner send, accounts credit, denied role, rendered report/email and mobile layout; run the required Vite build. Independent reviewers inspect actual source/diff.

No live email, payment, new provider account, production deployment, statutory tax calculation, official tax certificate or consultant invoice is implied by these tests. Existing pending acceptance contracts stay pending unless the complete corresponding behavior is proved. In particular, consultant invoices, PTO ledger and bank remittance documents remain separate required work.
