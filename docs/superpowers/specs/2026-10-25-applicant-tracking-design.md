# Applicant tracking in Miru

Source: [Sonam's #2463](https://github.com/saeloun/miru-web/issues/2463). This design preserves all ten requested areas; completing one implementation task does not complete the issue.

## Approach

Build hiring in the existing Rails/React app, using PostgreSQL, Pundit, private Active Storage, Action Mailbox, Action Mailer and the existing job queue. The branch builds on the tested generic document-signing branch so onboarding can use uploaded agreements. This is an implementation choice under the user's instruction to continue implementing Sonam's issues, not a claim that unconfirmed company policies were approved.

Use a unique inbound address for each configured company mailbox. An operator can forward applications from the three inboxes in the issue through Rails' authenticated relay ingress; retain the originating mailbox and original receipt metadata. Admins can also add an application or upload/mark an email manually. Do not require full Gmail access, a paid ATS, an external classifier or a code runner. Gmail OAuth would add restricted mailbox access and account setup; a separate ATS would split hiring from Miru's records and agreements.

## Data and permissions

- A company owns candidates, applications, roles, mailbox routes, hiring settings, assignment templates/instances, interviews/feedback, offers, communications and activity history.
- A candidate is unique by company and normalized email. Do not merge by name, remove plus addressing, or infer identity across companies. A candidate can have several applications; repeated deliveries preserve source history without duplicating an application or acknowledgement. Conflicting profile details need explicit reconciliation.
- Owner/Admin with an active staff membership manages hiring. An interviewer/reviewer sees only assigned applications and the material required for assessment. Compensation is excluded unless Admin grants it explicitly; grants end when membership/assignment ends.
- Candidate portal capabilities are scoped to one application, expiring and revocable, and checked on every read/write/download. Follow the existing private review page: token in the URL fragment, POST exchange, CSRF, no telemetry, no-store/no-referrer headers, filtered parameters and safe attachment downloads. Never serialize internal notes or feedback to the portal.
- Validate tenant ownership of every role, owner, interviewer, assignment and attachment. Recheck authorization and workspace under mutation locks. Database uniqueness protects identities and idempotency; optimistic versions protect edits.
- Candidate compensation and sensitive custom answers use encrypted details, following EmployeeRecord. Raw bodies, tokens, compensation and attachments do not enter audit changes or logs. Events record actor, action, IDs and time; permitted hiring users can see the separately protected history.
- Private uploads are bounded and validated before persistence. Serve attachments through authorized domain endpoints as downloads with sandbox/nosniff headers. Never execute submitted code, fetch repository URLs or extract archives automatically. Candidate submissions do not create public blob URLs.

## Sending and intake reliability

Use a persisted communication operation with a unique application/event key and a frozen recipient/content snapshot. Queue acceptance, delivery attempt and confirmed delivery are separate facts. SMTP cannot guarantee exactly-once delivery after an ambiguous network/process failure: flag it for reconciliation and do not blindly retry. A permission change, withdrawn application, revoked portal link or stale approved template blocks an unsent operation. Candidate and internal message renderers take explicit permitted fields, not a model dump.

Intake limits and route authentication apply before MIME processing. Accept only explicitly configured mailbox destinations; do not route by an untrusted company ID or displayed sender. Normalize duplicate identity per company with database constraints, preserving each observed mailbox receipt. Treat the sender and attachments as untrusted, and quarantine uncertain application classification for Admin review. Native Action Mailbox's global message deduplication must not erase tenant/mailbox receipt history.

## Rollout and evidence

First deliver the manual intake/list/detail/role workflow with no outgoing mail, then integrate email/forms, assessment, interviews, decisions/onboarding and reporting/retention. Keep every remaining issue requirement visible in the plan. Each task needs focused RED→GREEN checks; trust boundaries need request/policy tests and actual browser evidence. Use synthetic candidates, an isolated DB and local mail capture; no real candidates, external signature requests or production mailbox configuration during implementation.

Before launch, Admin must approve the introduction/client count, role overlap windows, engagement-specific PTO wording, assignment limits/AI-use policy, feedback deadlines and rejection automation. These are editable configuration gates, not guessed company facts.

Release requires the actual intake→portal→assessment/interview→offer→onboarding journey, privacy/retry/deletion tests, desktop/mobile and keyboard checks, PDF/download checks where used, required Vite build, fresh reviews, exact-head CI, preserved private-production changes and an immutable image. Do not close #2463 until every row above has evidence; no production or integration success claim from mocks alone.
