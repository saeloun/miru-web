# Client legal and agreement contacts

This implements the client onboarding data from Sonam's #2462 and connects its billing data to existing invoice views and recipient selection. Full editable contracts, templates, approvals, document versions and signing remain required subsequent work in that issue; this change does not present those workflows as implemented.

Use five optional Client columns: legal_name, finance_email, signatory_name, signatory_designation, signatory_email. Existing email remains the primary contact and existing current_address is the registered company address used by invoices. Keep existing clients editable with these fields unset; future agreement send validation must require the applicable legal/signatory details. Legal names and designations accept Unicode and up to255characters; the two new emails accept up to254characters and use the existing Devise email validation. Trim values and persist blanks as nil. No new uniqueness on legal names or finance/signatory emails.

Extend owner/admin create/update/show through the existing scoped client controller, policy, presenter and desktop/mobile forms. Add one shared agreement-fields component, matching existing form controls and accessibility. Show the values in client details. A one-time Copy finance email action fills signatory_email; the stored fields remain independent when either address changes later. No signing request, consent or contact invitation is implied by entering data.

Configured finance_email joins the existing invoice-recipient helper's result, deduplicated case-insensitively. Preserve accepted members and the current virtual-verified-invitation switch; never select a recipient merely because signatory_email is set. Existing contacts still receive their current invoice messages. The form must explain this delivery use. No actual emails are sent by implementation or QA.

Legal name appears in billed-to views/previews/PDFs, falling back to existing name when absent. Keep client lists/selectors using the current display name. Follow each existing API's snake/camel key convention; do not expose signatory contacts through shared/public invoice payloads. Existing invoices currently read live Client details rather than retained recipient snapshots; this change follows that behavior. Immutable agreement versions will require their own snapshots and must not reuse it.

Approaches considered: explicit columns fit the five known attributes and existing Client permissions/forms; a JSON blob adds validation/serialization indirection, while a separate contact/legal-entity domain is unnecessary for this onboarding unit. This is the implementation choice under the user's existing instruction to continue choosing, implementing, testing and shipping; no new subscription or provider dependency is needed.

Use real local Brave desktop/mobile save/reopen/error flows and an actual synthetic PDF, plus the required Vite build. Publish only synthetic screenshots. Keep external signing/provider and ATS/payroll requirements open.
