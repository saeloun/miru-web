# Google Calendar import — Task 6 increment

Local implementation for [Sonam's ATS request](https://github.com/saeloun/miru-web/issues/2463). Admins import an existing meeting through their own authorized Google connection. This does not create/change a Google event, send candidate mail or complete Task 6; feedback, communications and reminders remain unfinished.

## Behavior

- Booking history opens calendar import on request. Unconfigured/disconnected connections explain the manual fallback. OAuth returns to the application through a state-bound, strictly allowed local path; external, malformed and callback-supplied return paths are ignored. Existing calendar and hiring routes share one owner-bound connection implementation.
- Calendar and event pages contain at most 20 records. Event searches span seven UTC days and filter for the current candidate, all assigned interviewers and the configured round duration. The organizer counts as a participant; explicitly declined attendees do not. Email aliases are not inferred. Unrelated meeting titles/descriptions and attendee lists are excluded from hiring responses.
- Google is fetched again when importing. The event ID/etag, required participants, current active panel grants/employment, candidate identity, Admin/workspace and optimistic application/round versions are checked. Provider I/O occurs outside the scheduling locks; authorization and context are checked again afterward.
- Already accepted requests recover by their original UUID and exact intent before another provider call or connection check. Changed intent conflicts. Losing the response does not create a second booking or read Google again. Recovery still requires current Admin access.
- Imported UTC instants preserve seconds and microseconds in PostgreSQL and API responses; candidate-local time and offset remain explicit. Finer precision, all-day/cancelled events, repeating masters, incomplete attendee lists and mismatched durations are rejected. A single recurring instance is supported. Manual replacement of an imported booking requires choosing a new time rather than silently truncating its original time.
- Replacing a booking preserves the original and requires a reason. Invalid URLs/replacements roll back cancellation. Staff see only the curated booking projection; provider IDs/etag, internal reasons and frozen Admin snapshots stay private. Calendar/event request identifiers are filtered from request logs; token/cursor filtering uses the existing token filter.
- Provider reads have bounded connection/read timeouts. Throttling, transport timeouts and server errors are retryable; missing events and revoked connections have separate outcomes. Raw provider error messages are not returned. No new dependency or Google write scope was added.

## Decisions and costs

1. Match actual participant email addresses and count a non-declined organizer, rather than infer aliases. Cost: aliases/unmatched bookings require correction in Google or explicit manual recording.
2. Preserve the configured round duration and PostgreSQL microsecond precision rather than rewrite issued terms or round times. Cost: different-duration or finer-precision events require an explicit adjustment/manual choice before recording.
3. Use bounded seven-day searches and 20-item pages rather than downloading an entire private calendar. Cost: sparse matches can require more pages or another date.
