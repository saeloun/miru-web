This records the offer-record and private-response checkpoint for [Sonam's selection/onboarding requirements](https://github.com/saeloun/miru-web/issues/2463). The subsequent [approved offer-email increment](offer-email-20261108.md) now covers email delivery controls. Task 8 remains incomplete for the accepted-offer→employee/consultant→generic agreement handoff. No production or external delivery is established here.

## Behavior

- A current finalized Pass selection permits one active Preparing offer. Admin saves engagement (employee/consultant), title, approved compensation amount/currency/monthly-or-annual period, proposed joining date and expiry date. Unknown currencies, fractional unsupported minor units, floats, nonpositive amounts, malformed dates and unsupported engagements/periods are rejected.
- Draft creation/editing recover exact accepted intent after a lost response; different stale intent conflicts. The UI preserves unsaved terms, freezes unresolved requests and exposes an unchanged retry. A private capability is not exposed for a Preparing draft.
- Separate approval of unchanged saved terms issues the offer and moves the application to Offer. Issued terms, recipient/name/company snapshot and saved IANA expiry zone are immutable. **Sent means the private offer was issued; no email is sent by this increment.** The UI says this explicitly. Future offer-email delivery must retain its own outbox status.
- A candidate's expiring private fragment link is exchanged through CSRF-protected POST requests. The entrypoint removes the fragment from the current URL. The standalone page contains only the issued terms/identity and response status, with no application notes, selection reasons, assessments, interviewer data or analytics client.
- Candidate confirmation records Accepted or Declined against the exact issued version. Identical accepted intent recovers once; changing an existing response conflicts. Acceptance does not create users/profiles, set payroll compensation, issue an agreement or send mail.
- Revocation, expiry, source-email changes, reopened selection and withdrawn/rejected applications make the capability unavailable. Changing the issuer's workspace or later removing their Admin role does not revoke already issued company terms; this follows Miru's existing private-link lifecycle. Current Admin authority is still required for every management action. A denied reload removes previously displayed private terms. Existing Admin pages clear the whole private candidate view on scoped denial.
- Expiry is enforced at the saved local date boundary before any candidate read/write, independently of the five-minute expiry sweep. A replacement can be prepared immediately after expiry even if the sweep has not run; the preparation transaction records the expired predecessor first. Accepted offers remain active until the later onboarding workflow handles them.
- Actor→company→application→offer locks protect Admin mutations. Candidate response uses company→application→offer locks. PostgreSQL enforces one active offer, tenant request identity, lifecycle consistency and the composite application/company foreign key. Terms, request intents, capability and issuance/response snapshots are encrypted and filtered; audit changes contain lifecycle metadata.
